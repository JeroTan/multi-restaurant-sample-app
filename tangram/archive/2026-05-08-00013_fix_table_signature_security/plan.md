# Feature Roadmap: 00013_fix_table_signature_security

## I. Architectural Alignment
- **Security Pillar**: Table URLs MUST use HMAC signatures to prevent forgery. Websocket connections MUST be authorized.
- **Stack Pillar**: Implementation must use Cloudflare Worker compatible crypto (Web Crypto API) encapsulated in dedicated utilities.
- **Project Knowledge**: Follows the convention of centralizing crypto logic in `src/lib/crypto/**`.

## II. Data Model & Schema Changes
- No schema changes required. We will use the existing `qrCodeSignature` field in the `tables` table.

## III. Atomic Task List

### Layer: Crypto Foundation
- [x] **Create Signature Utility**
  > **Detailed Summary:** Create `src/lib/crypto/signature.ts`. Implement `signTableSignature` and `verifyTableSignature` using the Web Crypto API. This utility should handle the concatenation of `tenantId` and `tableNumber` consistently. It will replace the fragmented logic in `src/lib/utils.ts`.

- [x] **Secret Enforcement Utility**
  > **Detailed Summary:** Modify `src/lib/cloudflare.ts` to include a helper `getRequiredSecret(name: string)` that throws a descriptive error if a secret is missing, instead of falling back to insecure hardcoded strings.

### Layer: API & Logic
- [x] **Refactor Admin Table Creation API**
  > **Detailed Summary:** Modify `src/app/api/admin/tables/route.ts` to use the new `signTableSignature` utility. Ensure it uses `getRequiredSecret('JWT_SECRET')`.

- [x] **Refactor Customer Order API**
  > **Detailed Summary:** Update `src/app/api/customer/orders/route.ts` (both GET and POST handlers) to use `verifyTableSignature`. Improve logging to capture masked versions of the secret/signature in case of a mismatch to aid remote debugging.

### Layer: Websocket & Real-Time
- [x] **Secure Websocket Handshake**
  > **Detailed Summary:** Modify `src/worker.ts` and `src/components/CustomerMenuClient.tsx`. The Websocket connection should now include the `signature` in the query params. The worker will verify the signature before upgrading to a Websocket, ensuring only legitimate table users can join the real-time hub.

### Layer: UI & Demo
- [x] **Update Demo Generation**
  > **Detailed Summary:** Modify `src/components/CreateDemoButton.tsx` to ensure the signatures it receives from the updated Admin API are correctly passed to the customer URL and subsequenly to the Websocket connection.

- [x] **Cleanup Utilities**
  > **Detailed Summary:** Remove `signTableUrl` from `src/lib/utils.ts`. Update all remaining imports to the new `src/lib/crypto/signature.ts` location.

## IV. Critical Path & Dependencies
- The **Signature Utility** and **Secret Enforcement** are blockers for all other tasks.
- Websocket security depends on the API refactoring to ensure signatures are available in the client.

## V. Verification & Testing Mechanism (MANDATORY)

| Requirement | Verification Method | Pass Criteria |
| :--- | :--- | :--- |
| **Signature Consistency** | Unit Test / Script | Signature generated by `signTableSignature` matches verification by `verifyTableSignature` for the same inputs. |
| **Admin Flow** | Manual Test | Creating a table in Admin UI generates a valid signature in the database. |
| **Customer Flow** | Manual Test | Customer can load menu and submit order using the signature provided in the URL. |
| **Websocket Security** | Manual Test | Websocket fails to connect if an invalid signature is provided. |
| **Secret Hardening** | Manual Test | Removing `JWT_SECRET` from `.env` or Wrangler config results in a clear error message instead of failing silently with a fallback. |
